### 1. 해결 원리: "복사본"에서 "참조(Link)"로 변경

유니티 Addressables 시스템은 에셋을 두 가지 방식으로 처리합니다.

* **이전 상황 (Implicit Dependency - 암시적 의존성):**
* 공용 텍스처(C)가 Addressable 그룹에 등록되지 않음.
* 번들 A가 C를 필요로 함 -> **C를 복제해서 A 안에 넣음.**
* 번들 B가 C를 필요로 함 -> **C를 또 복제해서 B 안에 넣음.**
* **결과:** 물리적으로 서로 다른 2개의 파일이 생김.


* **Shared 그룹 등록 후 (Explicit Dependency - 명시적 의존성):**
* 공용 텍스처(C)를 'Shared Group'에 등록함 (즉, Addressable로 만듦).
* 번들 A가 C를 필요로 함 -> **"C는 다른 번들에 있으니 거기를 참조해"라고 링크만 건다.**
* 번들 B가 C를 필요로 함 -> **"C는 저쪽 번들에 있어"라고 링크만 건다.**
* **결과:** C는 'Shared Group' 번들에 딱 하나만 존재함.



### 2. 자동으로 처리되는 것들

사용자가 별도의 코드를 작성하지 않아도 Addressables 시스템이 다음을 자동으로 수행합니다.

1. **자동 로딩:** 게임 실행 중 `번들 A`를 로드하려고 할 때, 유니티는 "어? 이거 `Shared Group`에 있는 텍스처가 필요하네?"라고 판단하고 **자동으로 `Shared Group` 번들을 먼저 메모리에 올립니다.**
2. **메모리 관리:** `번들 A`와 `번들 B`가 모두 언로드(Unload) 되어 더 이상 `Shared Group`의 텍스처를 참조하는 곳이 없을 때, 비로소 `Shared Group`도 메모리에서 내려갑니다(Ref Count 기반).

---

### 3. 더 확실한 관리를 위한 "Analyze" 도구 사용법 (추천)

매번 리포트(Report) 창을 보고 수동으로 옮기는 것은 번거롭습니다. 유니티는 이를 자동으로 찾아주는 도구를 제공합니다.

1. **Analyze 창 열기:**
* 메뉴: `Window` > `Asset Management` > `Addressables` > **`Analyze`**


2. **중복 검사 실행:**
* `Check for Duplicate Bundle Dependencies` 항목을 찾습니다.
* **[Fix Selected Rules]** 버튼을 누르면 자동으로 중복된 에셋들을 찾아 별도의 그룹(보통 `Duplicate Asset Isolation`)을 만들어 몰아넣어 줍니다.
* *(물론, 수동으로 'Shared Assets' 그룹을 만들어 관리하는 것이 폴더 정리상 더 깔끔할 수 있습니다.)*



### 4. 주의할 점 (Trade-off)

Shared 그룹으로 분리하는 것이 무조건 정답은 아닙니다. 상황에 따른 전략이 필요합니다.

* **번들 의존성 복잡도:** Shared 그룹이 너무 거대해지면, 아주 작은 아이콘 하나를 쓰려고 거대한 Shared 번들 전체를 로드해야 할 수도 있습니다.
* **해결책:** 공용 자원이 너무 많다면 `Shared_Textures`, `Shared_Sounds` 처럼 종류별로 나누거나, 자주 같이 쓰이는 것끼리 묶는 것이 좋습니다.

### 요약 및 다음 단계

1. **네, Shared 그룹에 넣는 것만으로 빌드 용량 중복 문제는 해결됩니다.**
2. 이후 **Build > New Build**를 수행해야 실제 번들에 반영됩니다.
3. 앞으로는 빌드 전에 **`Analyze` 툴**을 한번 돌려서 중복 의존성이 없는지 체크하는 습관을 들이시면 좋습니다.
