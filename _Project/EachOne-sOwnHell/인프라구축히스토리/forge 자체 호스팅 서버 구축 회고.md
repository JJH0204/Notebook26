## 2. 문제 → 대응 → 결과

### 2-1. 구조적 문제 (설계를 바꾼 것)

| # | 문제 | 대응 | 결과 |
|---|---|---|---|
| 1 | **WSL 배포판이 유휴 시 종료** — VM 은 살아 있는데 배포판이 죽어 systemd·docker·컨테이너가 전부 정리됨. `vmIdleTimeout` 으로 못 막음 | `wsl.exe ... sleep infinity` 를 상주시키는 keep-alive 작업. 실행시간 제한을 **무제한(PT0S)** 으로 | 무인 운영의 전제 성립. 부팅 +77초에 스택 자동 복구 |
| 2 | **Tailscale 무인 모드 기본 꺼짐** — GUI 사용자가 로그아웃하면 tailnet 연결이 끊김. 05:00 재부팅 후 **5시간 불통** | `tailscale set --unattended=true` | 로그아웃 구간에 남은 로그 2건으로 도달성 실증 |
| 3 | **WSL 의 9p 마운트가 로그아웃으로 끊김** — 마운트 목록엔 남는데 I/O 에러. **백업 저장소가 F: 라 백업이 통째로 실패** | 백업 스크립트에 마운트 검사 + `umount -f/-l` → `mount -t drvfs` 자동 재연결 | 일부러 끊고 시험 → 자동 복구 후 RC=0 |
| 4 | **DB crash recovery** — 그냥 `shutdown /r` 하면 WSL VM 이 급살당함 | 컨테이너 정상 종료 → `wsl --shutdown` → 재부팅 순서 | 같은 머신 두 재부팅이 정반대 결과로 실증 |
| 5 | **백업과 재부팅이 분리되어 겹칠 위험** (04:30 백업 / 05:00 재부팅) | 05:00 단일 작업으로 순차 실행 | repo 가 커져도 겹치지 않음 |

### 2-2. 설정이 "들어갔지만 동작하지 않은" 문제

| # | 문제 | 대응 | 결과 |
|---|---|---|---|
| 6 | Gitea 가 읽지 않는 gitconfig 에 크기 제한을 넣음 (`/data/git/.gitconfig`, 실제로는 `HOME_PATH` 의 것만 사용) | app.ini `[git.config]` 섹션으로 이동 | 600MB push 거부 / 50MB 통과 실증 |

## 3. 반복된 실패 패턴

개별 버그보다 이쪽이 중요하다. 같은 유형이 반복해서 나왔다.

### 패턴 A — "설정했다"와 "동작한다"를 혼동 (3회)
6번(gitconfig), 7번(환경변수 인코딩), 2번(Tailscale 무인모드). 셋 다 **파일에는 값이 있었고, 실제로는 적용되지 않았다.**
→ **설정 확인이 아니라 동작 시험을 검증 기준으로 삼는다.** 600MB push, 로그아웃 후 도달성, 섹션명 육안 확인.

### 패턴 B — 관측하지 않은 구간을 관측한 것처럼 단정 (1회, 대가가 컸음)
`tailscaled` **프로세스가 부팅 18초 후 떴다**는 사실만으로 "Tailscale 은 로그인과 무관하다"고 결론냈다. HTTP 도달성 확인은 **전부 로그인 이후에** 해놓고 로그인 전 구간까지 단정했다. 사용자가 두 번 의문을 제기했고 두 번 다 옳았다. 결과는 5시간 불통.
→ **무인 동작을 주장하려면 무인 구간에 남은 로그를 근거로 한다.** `healthcheck.log` 가 30분마다 남기는 기록이 정본이다.

### 패턴 C — 확인 가능한 것을 추정으로 전제 (4회)
- "Google Drive 무료 15GB" → 실제 **5TB 계정**(`rclone about` 한 번이면 알 수 있었음)
- "rclone 1.75 부터 client_id 필수" → 화면만 보고 오진, 실제 원인은 scope 프롬프트 입력 오류
- "NAS 는 전량 소실 전력이 있어 신뢰도가 낮다" → **원인은 4GB 장비에 풀스택을 올린 것**이지 저장 장치의 실패가 아님
- grep 결과 0건으로 "Plane UI 에 Gitea 지원이 없다" 추정 → **모든 공급자가 0건**이었으므로 근거가 될 수 없었음(실제로는 지원됨)
→ **제약은 조회한다.** 한 번의 조회로 답이 나오는 것을 추정하지 않는다.

### 패턴 D — 사람의 실시간 개입이 필요한 검증은 그 자체가 실패 요인 (3회 실패 후 성공)
무인 재부팅 검증을 "재부팅 후 폰으로 확인해 달라"로 설계했더니 **3번 연속** 사용자가 조급해져 먼저 로그인하면서 오염됐다. 4차에서 **"5분간 로그인만 하지 말 것"** 으로 바꾸고 타임스탬프로 사후 판정하니 한 번에 성공했다.
→ **검증 절차에서 사람이 할 일을 최소화하고, 판정은 기계가 남긴 기록으로 한다.**

### 패턴 E — 실행 환경의 특성을 모른 채 결론 (3회)
- **MSIX 가상화** — Claude 앱 컨테이너의 PowerShell 이 `%APPDATA%` 의 가상 사본을 읽어 "인증 실패"로 오진. 실제 설정은 멀쩡했다
- **PowerShell 변수 대소문자 미구분** — `$RC`/`$rc` 충돌
- **`docker logs` 누적** — 이전 기동 로그에 매칭되어 crash recovery 2회 오진
→ **도구가 내 예상대로 동작한다고 가정하지 않는다.** 이상하면 우회 경로로 교차 확인한다(WSL 로 Windows 파일 읽기 등).

## 4. 잘 작동한 것

- **동작 검증을 실제로 수행한 것.** 600MB push, 복원 리허설, 로그아웃 프로브 — 전부 여기서 결함이 드러났다. 설정만 확인했으면 전부 놓쳤다.
- **실패를 크게 울리도록 설계한 것.** 백업 스크립트가 `RC=2` 로 마운트 문제를 정확히 보고했고, 헬스체크가 5시간 장애를 30분마다 기록했다(알림 채널이 없어 사람에게 닿지 않았을 뿐).
- **NAS 사고의 근본 원인을 처음부터 차단한 것.** `receive.maxInputSize`, `mem_limit`, LFS 강제. 실제로 이관된 repo 는 LFS 규칙이 639·924건으로 건전했다.
- **되돌릴 수 있게 만든 것.** app.ini 백업, compose 백업, ACL 버전 히스토리, 각 단계 롤백 절차.

## 5. 개선안

### 5-1. 즉시 반영할 작업 방식

| # | 개선안 | 근거 패턴 |
|---|---|---|
| 1 | 검증 기준을 **설정 확인 → 동작 시험**으로. "값을 넣었다"는 완료가 아니다 | A |
| 2 | 무인 동작 주장은 **무인 구간에 남은 로그**로만. 프로세스 생존은 근거가 아니다 | B |
| 3 | 한 번의 조회로 알 수 있는 제약은 **추정하지 않는다** | C |
| 4 | 검증 절차는 **사람의 실시간 개입을 최소화**하고 사후 판정 가능하게 설계 | D |
| 5 | 이상 징후가 나오면 **우회 경로로 교차 확인** 후 결론 | E |
| 6 | **이미 보유한 자원을 먼저 검토**하고 제안한다(NAS 건) | C |
| 7 | 판정식에서 **"모른다"와 "나쁘다"를 분리**한다 | 13번 |

### 5-3. 운영 중 지켜볼 것

- **로그아웃 시 `/mnt/f` 끊김** — 자동 재마운트를 넣었으나 실제 로그아웃 사례로는 미검증. 발생 시 `backup.log` 의 재마운트 로그 확인
- **`01-Boot-Start` 실행시간 제한** — 반드시 `PT0S`. 기본값(3일)이면 사흘 뒤 서버가 조용히 죽는다
- **rclone client_id** — client **secret** 회전은 안전(파일 계속 보임). **client_id 변경만** 기존 업로드를 고아로 만든다
- **restic 비밀번호** — `/srv/backup/.restic-pass`. **repo·LFS 19GB 는 restic 에만 있다**(F: 평문 덤프는 DB 뿐). 이 비밀번호를 잃으면 코드·에셋 복구 불가
