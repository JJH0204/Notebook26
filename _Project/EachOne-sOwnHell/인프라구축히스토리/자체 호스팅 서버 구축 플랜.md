### Phase 1 — WSL2 배포판 구축 (E: 드라이브) (1시간)

**작업**
1. `C:\Users\jhjy5\.wslconfig` 작성:
   ```ini

   memory=16GB
   processors=4
   swap=8GB
   networkingMode=mirrored
   dnsTunneling=true
   firewall=true
   autoProxy=false

   (48GB 중 16GB만 할당 — 이 PC는 데스크톱 겸용. Gitea+Plane 실사용 피크는 4~6GB 예상.)

   systemd=true
   [user]
   default=srv
   [interop]
   appendWindowsPath=false

4. docker engine 설치(공식 apt repo), `systemctl enable --now docker`, 사용자 docker 그룹 추가.

`networkingMode=mirrored`는 WSL이 호스트 인터페이스(Tailscale 포함)를 직접 공유하게 해서 포트 노출을 단순화하지만, Tailscale과의 조합에서 문제가 보고된 적 있다. **롤백**: `.wslconfig` 삭제 → `wsl --shutdown`. 배포판은 `wsl --unregister srv`로 완전 제거(E: 디렉터리 삭제)

### ⚠ 중대 발견 — WSL 배포판의 유휴 종료 (설계 변경 사항)

**증상**: 컨테이너를 `-d`로 띄우고 세션이 끊기면 몇 초 뒤 컨테이너가 `Exited (0)`가 된다.

**원인**: WSL은 **유틸리티 VM은 유지하면서 배포판은 유휴 시 종료**한다. 배포판이 종료되면 systemd와 그 아래 docker·컨테이너가 전부 정리된다(그래서 정상 종료 코드 0). 실측: `uptime`은 16분인데 `wsl -l -v` 상태는 `Stopped`, 컨테이너는 죽어 있음.

**`vmIdleTimeout`으로 막을 수 없다** — 그건 VM 수준 설정이고, 여기서 죽는 건 배포판이다.

**해결**: 배포판을 붙잡아 두는 **상주 프로세스(keep-alive)** 가 필수다.
```powershell
Start-Process -FilePath "wsl.exe" -ArgumentList '-d','srv','-u','root','--','sleep','infinity' -WindowStyle Hidden
```
이 `wsl.exe` 클라이언트 프로세스가 살아 있는 동안 배포판이 `Running`으로 유지된다. 적용 후 `Running` 유지 확인됨.

**Phase 6 설계에 미치는 영향(중요)**
- `Selfhost\01-Boot-Start` 작업은 "컨테이너를 up 하고 끝"이 아니라 **keep-alive 프로세스를 상주시키는 작업**이어야 한다. 작업이 끝나 프로세스가 종료되면 배포판째로 내려간다.
- 따라서 해당 작업은 트리거 실행 후에도 **계속 실행 상태로 남아야** 하며, "작업을 중지할 시간" 설정을 꺼야 한다.
- 컨테이너에는 `--restart always`를 반드시 부여한다(배포판 재기동 시 자동 복구).
- **현재 keep-alive는 임시 수동 실행 상태** → 재부팅하면 사라진다. Phase 6에서 작업 스케줄러로 정식화 필요.

**부수 교훈**: 테스트 컨테이너를 `/tmp` 바인드 마운트로 띄웠더니 배포판 재기동 후 `/tmp`가 비워져 `Exited (127)`. **컨테이너 데이터는 절대 `/tmp`에 두지 말 것** — `/srv` 아래 고정.

##### ⚠ 이 단계에서 저지른 실수 2건 (재발 방지용 기록)

**실수 1 — Gitea가 읽지 않는 gitconfig에 설정을 넣었다.**
NAS 시절 기억(`/data/git/.gitconfig`)을 그대로 적용했으나, 현재 Gitea는 `[git] HOME_PATH`(기본 `/data/gitea/home`)의 gitconfig만 사용한다. `/data/git/.gitconfig`에 `receive.maxInputSize`가 멀쩡히 들어 있고 `git config --list`에도 보였지만 **서버는 무시했고 600MB push가 그대로 통과**했다.
→ **교훈: git 관련 설정은 반드시 app.ini `[git.config]` 섹션으로 넣는다.** Gitea가 자기 gitconfig에 써 준다. 검증은 `docker exec gitea cat /data/gitea/home/.gitconfig`.

**실수 2 — 환경변수의 점(.) 인코딩을 틀렸다.**
`GITEA__cron_002Erepo_health_check__ENABLED` 로 썼더니 app.ini에 `[cron.repo_health_check]`가 아니라 **`[cron_002erepo_health_check]`라는 존재하지 않는 섹션**이 생성됐다. 즉 지난 NAS OOM의 트리거였던 데일리 self-fsck가 **꺼진 줄 알았지만 계속 켜져 있었다.**
→ **교훈: 점이 들어간 섹션은 환경변수로 다루지 말고 app.ini에 직접 쓴다.** 설정을 넣은 뒤에는 반드시 `grep -E '^\[' app.ini`로 **섹션명이 의도대로 만들어졌는지 눈으로 확인**한다. "환경변수를 넣었다"와 "설정이 적용됐다"는 다른 사건이다.

**공통 교훈**: 두 실수 모두 "설정 파일에 값을 썼다"에서 멈췄으면 발견되지 않았다. **동작을 실제로 시험하는 검증(600MB push)이 있었기 때문에 드러났다.** 이후 단계에서도 설정 확인이 아니라 동작 검증을 기준으로 삼는다.

**부수**: SSH clone 최초 실패는 서버 문제가 아니라 키 등록 직후 `authorized_keys` 기록 전에 clone한 테스트 타이밍 문제였다(대기 추가 후 통과).

**산출물**
- `/srv/gitea/{docker-compose.yml, .env}` (`.env`는 0600, POSTGRES_PASSWORD 랜덤 생성)
- `/srv/gitea/data/gitea/conf/app.ini` (+ 수정 전 백업 `app.ini.bak.*`)

### ⚠ 2026-08-07 2차 발견 — WSL 의 /mnt 마운트가 로그아웃으로 끊긴다

무인 모드 검증차 로그아웃했다 돌아온 뒤, `/mnt/c` `/mnt/f` 가 **마운트 목록에는 있는데 접근하면 I/O 에러**인 상태가 됐다.
```
mount | grep 9p  →  C:\ on /mnt/c type 9p (... rfd=13,wfd=13)   ← 항목은 존재
ls /mnt/f        →  Input/output error
```
**원인**: WSL 의 drvfs(9p) 마운트는 배포판을 띄운 **세션의 파일 디스크립터에 묶여 있다.** 로그아웃하면 그 전송 채널이 죽는다. 배포판·systemd·컨테이너는 멀쩡히 살아남으므로 **컨테이너만 보면 정상으로 보인다.**

**왜 심각한가**: **백업 저장소가 `F:\selfhost-backup` 이다.** 이 상태로 04:30 이 되면 백업이 통째로 실패한다.

**복구**: 배포판 재시작(`wsl --shutdown` → keep-alive 재기동)으로 마운트가 재생성된다.

**적용한 방어 (`selfhost-backup.sh`)**
1. **마운트 가드**: restic 전에 `/mnt/f` 읽기·쓰기를 실제로 시험하고, 실패 시 `RC=2` 로 종료하며 restic 을 건너뛴다. (그냥 두면 restic 이 알아보기 힘든 방식으로 실패한다)
2. **pg_dump 는 마운트와 무관하게 먼저 수행**되어 `/srv/backup/dump`(ext4)에 남는다 → 마운트가 깨져도 복구 자체는 가능.
3. `RC=2` 는 05:00 재부팅 알림에 "**/mnt/f 마운트 끊김**" 으로 표시된다.

**해결 (2026-08-07 추가) — 자동 재마운트**
WSL 안에서 9p 채널을 새로 열 수 있음을 확인했다. 재마운트하면 **파일 디스크립터가 새로 발급**된다(`rfd=6` → `rfd=3`) — 죽은 채널을 버리고 새 채널을 얻는 것이라 정확히 필요한 동작이다.
```bash
umount -f /mnt/f 2>/dev/null || umount -l /mnt/f 2>/dev/null || true
mount -t drvfs "F:" /mnt/f
```
백업 스크립트의 마운트 가드가 접근 실패를 감지하면 위 절차로 **자동 복구를 시도**하고, 성공하면 그대로 백업을 진행한다. 실패해야만 `RC=2`.

**검증**: `umount -l /mnt/f` 로 일부러 끊고 백업 실행 → `WARN: 접근 불가 - 재마운트 시도` → `재마운트 성공 - 백업 계속` → **RC=0**.

> 단서: 이 시험은 `umount -l` 로 끊은 것이라 **실제 로그아웃으로 세션이 죽는 경우와 완전히 같지는 않다.** `-f`/`-l` 양쪽을 시도하고 새 채널을 여는 구조라 커버될 가능성이 높으나, 실패 시에는 `RC=2` 로 즉시 알림이 간다. **로그아웃 후 실제 사례가 발생하면 backup.log 의 재마운트 로그를 확인할 것.**

- 그래서 설정을 `selfhost\secrets\` 로 복사하고 `--config` 로 고정했다. 가상화 대상 경로가 아니라 문맥과 무관하게 같은 파일을 본다.

##### 설정 과정에서의 오진 기록
사용자의 첫 `rclone config` 시도가 실패했을 때 화면만 보고 "rclone 1.75 부터 client_id 가 필수로 바뀌었다"고 단정했으나, `rclone help backend drive` 확인 결과 **여전히 선택 항목**이었다("Leave blank to use rclone's shared client_id"). 실제 실패 원인은 **scope 프롬프트에서 메뉴 번호 `3` 이 값으로 저장된 것**(`scope = 3-drive.file`)이었다.
→ 해결: 프롬프트를 하나씩 타이핑하는 대신 **값을 명령줄에 직접 넣는 방식**으로 전환.
```
rclone config create gdrive drive scope=drive.file
```
사용자는 브라우저 승인만 하면 되고, 오타가 들어갈 자리가 없다.
**교훈**: 대화형 프롬프트를 사람에게 받아치게 하는 절차는 그 자체가 실패 요인이다(무인 재부팅 검증에서 이미 같은 교훈을 얻었다).

##### 자체 client_id 발급 (2026-08-08 완료)

공용 client_id 폐지 예고에 대응해 Google Cloud Console 에서 자체 OAuth client 를 발급했다.

**절차**: 프로젝트 생성 → Drive API 사용 설정 → OAuth 동의 화면 구성 → **앱 게시** → 사용자 인증 정보 → **데스크톱 앱** 유형으로 client 생성 → `rclone config update gdrive client_id ... client_secret ...`

**막힌 지점 1 — 게시하지 않으면 본인도 못 쓴다**
동의 화면이 "테스트" 상태면 **등록된 테스터만** 접근 가능해서 `403 access_denied` 가 난다.
→ **대상(Audience) 화면에서 "앱 게시"** 필수. `drive.file` 은 비민감 범위라 Google 심사 없이 게시된다.
→ 테스터 추가로도 당장은 되지만 **테스트 상태에서는 리프레시 토큰이 7일 후 만료**되어 매주 백업이 조용히 멈춘다. 자동화 용도로는 반드시 게시할 것.

**막힌 지점 2 — ⚠ client_id 를 바꾸면 기존 업로드가 안 보인다 (중요)**
`drive.file` 은 **"이 앱이 만든 파일만"** 접근하는 범위다. client_id 가 바뀌면 Google 입장에서 **다른 앱**이므로, 이전 client 가 올린 12.33GB 에 접근 권한이 없다.
```
lsd gdrive:forge-backup  →  directory not found     (파일은 Drive 에 그대로 있으나 rclone 이 못 봄)
```
→ 조치: Drive 웹에서 옛 `forge-backup` 폴더 삭제(+휴지통 비우기) 후 **전량 재업로드**. 순서를 지키지 않으면 같은 이름의 폴더가 두 개 생겨 어느 것이 유효한지 혼란스러워진다.
→ 대안이었던 "스코프를 `drive`(전체)로 확대"는 재업로드가 불필요하지만 백업 도구가 개인 Drive 965GB 전체에 접근하게 되므로 채택하지 않았다.

> **구분해서 기억할 것**: **client_secret 회전은 안전하다**(client_id 가 그대로이므로 파일이 계속 보인다). **client_id 변경만** 기존 데이터를 고아로 만든다.

### 2026-08-08 — 오프사이트 방향 재검토 및 용량 공지 추가

**결정: Google Drive 유지(A안).** 이미 동작 중이고 유지비가 없다.

##### 기록 정정 — NAS 를 "신뢰할 수 없다"고 쓴 것은 부정확했다
이전 기록에서 NAS 를 백업 대상 후보로 논하며 "전량 소실 전력이 있어 신뢰도가 낮다"고 썼으나, 사용자 지적대로 **원인과 결과를 잘못 이어붙인 표현**이다.
- NAS 가 데이터를 잃은 것은 **RAM 4GB 장비에 Gitea·Plane 풀스택을 올려 운영한 결과**이지, 저장 장치로서 실패한 것이 아니다.
- **파일 저장소로만 쓴다면 조건이 전혀 다르며, 백업 대상으로 충분히 좋은 선택지다.**
- 또한 NAS 는 공인 IP 가 다르므로(`175.112.167.4` vs 이 PC `116.40.194.24`) **진짜 오프사이트**에 해당한다.
→ 향후 오프사이트를 NAS 로 옮기거나 이중화할 경우, restic 저장소 구조는 그대로 두고 rclone 대상만 바꾸면 된다(SFTP 지원). 전환 비용은 낮다.
→ **교훈: 이미 보유한 자원을 먼저 검토하고 제안할 것.** 이번엔 외부 서비스부터 제안해 불필요한 우회를 만들었다.

##### 🐞 버그 — PowerShell 변수는 대소문자를 구분하지 않는다
`offsite-sync.ps1` 에서 rclone 실행 경로를 `$RC`, 동기화 종료코드를 `$rc` 로 두었더니 **같은 변수**가 되었다.
```powershell
$RC = 'C:\...\rclone.exe'
$rc = $LASTEXITCODE      # 성공 시 0 → $RC 도 0 이 됨
& $RC size ...           # → & 0 → "The term '0' is not recognized"
```
동기화가 **성공했을 때만** 용량 조회가 실패하는 기묘한 증상이었다(실패 시엔 rc≠0 이라 경로가 아닌 값이지만 어차피 그 분기로 안 감).
→ `$RCLONE` / `$syncRc` 로 분리. **PowerShell 스크립트에서 짧은 대문자 약어 변수는 충돌 위험이 있다.**

##### 🐞 rclone 의 `--json` 출력 형식이 명령마다 다르다
`size --json` 은 한 줄, `about --json` 은 **여러 줄로 pretty-print** 한다. "`{` 로 시작하는 줄만 고르기" 필터가 `about` 에서는 `{` 한 글자만 남겨 파싱이 깨졌다.
→ **처음 `{` 부터 마지막 `}` 까지를 통째로 잘라내는** 헬퍼(`ConvertFrom-RcloneJson`)로 통일. 두 형식을 모두 커버한다.
